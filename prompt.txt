# Frontend design & UX overhaul — prompt for coding agent

Paste everything below this line into your coding agent (Claude Code, Cursor, etc.) as one instruction.

---

## Context

You are working on **PALASH AI**, a hackathon prototype for an AI-powered vernacular
pedagogy and real-time translation tool for mother-tongue-based primary education
(Hindi ↔ Santali, for the PALASH multilingual education programme in Jharkhand).

Stack: React + Vite frontend, FastAPI backend. Existing frontend surfaces include a
dashboard, translator, lessons, flashcards, and worksheets. The backend is honest about
what's real: translation calls a real IndicTrans2 model when available, and speech
endpoints intentionally return `501` until ASR/TTS checkpoints are configured. **Keep
that honesty. Nothing you write in the UI should claim a capability that isn't actually
wired up.**

Right now the app works but doesn't look or feel like a finished product. Your job is a
**design and UX pass**, not a rebuild — preserve every existing route, component
contract, and API call. Improve how it looks, feels, and explains itself.

## Step 0 — audit before you touch anything

Before writing any code:
1. List every existing page/route and component in `frontend/src`.
2. Identify the current styling approach (plain CSS, CSS modules, Tailwind, styled-
   components, etc.) and work **within** it — don't introduce a second styling system
   unless the current one is genuinely unworkable for this task.
3. Identify anywhere the frontend already touches the microphone (`getUserMedia`) or
   sends user text/audio to the backend, and anywhere the backend actually stores or
   forwards data. You need this to write honest copy later (see Task 7) — don't invent
   data-handling claims, read the actual code.
4. Confirm `npm run build` passes on the current `main` before you start, so you have a
   clean baseline to diff against.

## Design brief

**Brand anchor:** the project is named after the Palash tree, Jharkhand's state flower —
known as the "Flame of the Forest" for its vivid orange-red blooms, and central to tribal
spring festivals (Sarhul, the Santhal Baha/flower festival). Use this as the actual root
of the visual identity instead of a generic tech-startup blue. The result should read as
warm, rooted, and human — not a corporate SaaS template, and not a gaudy "hackathon neon"
palette either.

### 1. Color palette

Balance one confident warm accent against calm, light, low-saturation neutrals. Starting
point (refine as needed, but keep this character — warm neutrals, one accent, WCAG AA
contrast on all text/background pairs):

```
--flame-50:  #FDF3EC   /* tinted hover/highlight surfaces */
--flame-100: #FBE1D0
--flame-400: #F0824A
--flame-500: #E2612B   /* primary brand accent — buttons, links, active states */
--flame-600: #C14A1C   /* hover/pressed state */
--flame-700: #973712   /* accent text on light fills */

--forest-500: #3F7D4A  /* secondary accent — secondary actions, success, lesson/flashcard tags */
--forest-600: #2E5735

--cream-0:   #FAF7F2   /* page background — never pure white */
--cream-50:  #FFFDF9   /* card/surface background */
--warm-200:  #E7E1D6   /* borders, dividers */
--warm-500:  #8A8375   /* secondary/muted text */
--charcoal-900: #2B2620 /* primary text — never pure black */

--danger-500: #C23B3B  /* errors — kept distinct from the flame accent so it still reads as "warning" */
```

Apply this as design tokens (CSS custom properties, or the Tailwind config if that's
already in use) — not hardcoded hex values scattered across components.

### 2. Typography

Two fonts, used consistently everywhere:
- A clean humanist sans-serif for UI chrome and body text (e.g. Inter, Manrope, or
  similar). This is the "clean font" — legible at small sizes, works for a teacher
  audience that may not be highly tech-literate.
- A slightly warmer display face for the landing page hero and section headings, to
  avoid a clinical/cold feel.

Important and easy to miss: this app actually renders **Hindi (Devanagari) and Santali
(Ol Chiki)** text, not just English chrome. Whatever font stack you set must fall back
correctly for both scripts — include `Noto Sans Devanagari` and `Noto Sans Ol Chiki` (or
verify the current font already covers Ol Chiki; most don't) in the stack so lesson and
translation content doesn't fall back to a mismatched system font.

### 3. Logo and brand consistency

Design one SVG mark — a simplified, flat, gradient-free abstraction of a Palash bloom or
flame (e.g. a small cluster of 2–3 curved petal/flame shapes in `--flame-500`/`--flame-
600`) — paired with a wordmark. Build it as **one shared component** used everywhere
(navbar, footer, favicon, loading state) rather than redrawn per page. It must stay
legible down to favicon size (16–32px); if the illustrative mark doesn't hold up that
small, fall back to a clean wordmark-only lockup with a small flame-colored accent shape.

### 4. Layered look

Give the app a consistent elevation system instead of flat pages:
- 2–3 shadow tokens (subtle, soft, no harsh drop shadows).
- Cards sit on `--cream-50` slightly "lifted" above a `--cream-0` page background.
- One consistent border-radius scale and spacing scale used everywhere, not per
  component guesswork.

### 5. Hover and click animations

- Hover: subtle lift or scale (~1.02×) and color shift, 150–200ms ease-out, on buttons,
  cards, and nav items.
- Click/press: quick scale-down (~0.97×) for tactile feedback.
- Entrance: fade+slide on mount/scroll for sections and lists (stagger flashcard/lesson
  grids slightly rather than animating all items at once).
- Wrap all of it in `prefers-reduced-motion` checks.
- Keep everything on `transform`/`opacity` only — this needs to stay smooth on the kind
  of low-end Android tablets this project targets, not just on a dev laptop.

### 6. Landing page

Build a proper landing/home page (currently missing) that a teacher or evaluator can
land on and immediately understand the product:
- Hero: what this is (an AI translation and lesson tool that lets Hindi-speaking
  teachers deliver mother-tongue instruction in Santali) and who it's for.
- A short "how it works" section connecting to the real features: translator, lessons,
  flashcards, worksheets — link these to the actual routes, don't invent new ones.
- Acknowledge the PALASH programme / NIPUN Bharat FLN context in a sentence or two —
  this grounds the product instead of reading as generic.
- Clear CTA into the dashboard/app.
- Must not claim live voice-to-voice translation is working if the backend still
  returns `501` for it — phrase this as "coming" or omit it, don't overclaim.

### 7. Footer transparency notice

Add a persistent, easy-to-find footer (or a linked panel) that plainly states, **based
on what you found in Step 0**, not assumptions:
- What data the app sends/uses (e.g. "text you enter is sent to our translation model;
  we don't store it beyond your session" — only if that's actually true of the current
  backend).
- If and only if the frontend actually requests microphone access somewhere: a plain-
  language note on why (e.g. "used only while you're actively recording, never in the
  background") — written to match what the code actually does today, including if mic
  features aren't live yet ("voice input isn't enabled in this prototype yet").
- A one-line note that this is a hackathon prototype, not an official government
  product, so it isn't mistaken for one.

## Non-negotiable constraints

- Every existing route, prop, and API call keeps working. This is a visual/UX pass, not
  a rewrite.
- Fully responsive — teachers may use tablets, not just desktops.
- Accessible: semantic HTML, visible focus states, alt text, keyboard navigation,
  contrast ratios that pass WCAG AA against the new palette.
- No copy anywhere overstates what's actually implemented (see backend `501`s above).
- No secrets/API keys hardcoded into frontend code.

## Build order

1. Design tokens (palette, type scale, spacing, radius, shadow, motion durations).
2. Shared components: `Logo`, `Navbar`, `Footer`, `Button`, `Card`, page shell/layout —
   this is what makes the look consistent "throughout the site" instead of page-by-page.
3. Typography setup, including Devanagari/Ol Chiki fallback stack.
4. Landing page.
5. Footer transparency content (after confirming real data/mic behavior).
6. Re-pass every existing page (dashboard, translator, lessons, flashcards, worksheets)
   to adopt the new tokens and shared components.
7. QA: `npm run build`, a responsive check at mobile/tablet/desktop widths, a
   `prefers-reduced-motion` check, and a contrast check on the new palette.

## Acceptance checklist

- [ ] One set of design tokens driving color/spacing/radius/shadow app-wide, no stray
      hardcoded hex values in components.
- [ ] One `Logo` component reused in navbar, footer, and favicon.
- [ ] Every interactive element has a hover and a click state.
- [ ] Landing page exists, explains the product accurately, and links to real routes.
- [ ] Footer discloses data/mic usage accurately for the app's *current* behavior.
- [ ] Hindi and Santali text render correctly, not as tofu/fallback boxes.
- [ ] `npm run build` passes.
- [ ] Reduced-motion users get a static (not broken) experience.
